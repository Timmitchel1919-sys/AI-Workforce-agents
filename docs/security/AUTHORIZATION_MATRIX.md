# Control Plane Authorization Matrix

Baseline: 2026-10-18. This matrix describes executable routes in `api/http-api.ts`; documentation-only routes are excluded. It is a static security inventory, not proof that a deployed environment is healthy.

## Enforcement chain

Except for `GET /api/health`, every request is rate-limited. Privileged patterns are App Check protected when server mode is `enforced` (`api/security/route-policy.ts:41-58`). `/api/me/access`, session revocation, and lockdown perform their specialized identity checks before the general handler. Every other route passes:

1. Firebase ID-token verification through the injected `OperatorDirectory`.
2. ACTIVE account resolution to `OperatorPrincipal`.
3. Static route capability checks where defined.
4. Query/command-service capability checks.
5. Project allow-list checks on project resources and scoped commands.
6. Security-policy/destructive-action gates for high-risk operations.
7. Structured audit/security-event recording for privileged decisions.

Frontend visibility is never authorization. Role capabilities are deny-by-default in `contracts/control.ts:120-220`.

## Negative-test coverage

Existing suites cover missing/invalid credentials, inactive accounts, insufficient capability, project isolation, App Check missing/invalid/unavailable, rate limiting, invalid payloads, approval failures, lockdown, secret redaction, and several idempotency/replay paths. Primary evidence: `tests/http-api.test.ts`, `api-security.test.ts`, `control-plane-security.test.ts`, `production-project-access.test.ts`, `destructive-action*.test.ts`, `execution-security.test.ts`, `release.test.ts`, and `lost-device-response.test.ts`.

## Uncovered or incomplete areas

1. No generated test proves that every future `COMMAND_METHODS` entry has matching route-security metadata. Domain services still authorize, but metadata drift is possible.
2. Read-route authorization is distributed across query methods; there is no single table-driven test enumerating every GET family and viewer/operator/admin outcome.
3. Expired Firebase tokens are represented through verifier failures in fakes; emulator-backed expiry/revocation timing remains unverified.
4. App Check production enforcement is configuration-dependent; unit tests verify modes, not the deployed setting.
5. ITSM/operations/governance services use service-specific role checks rather than one unified capability registry; document and test them as they evolve.
6. Resource existence and authorization often intentionally collapse to `404`; retain this anti-enumeration behavior in regression tests.
7. CORS/header tests cover the API. A Hosting CSP is not present in `firebase.json`; adding one requires testing Firebase Auth/App Check, video, fonts, and Three.js compatibility.
